## V1 — Explain the gross P&L jump — DONE 2026-10-20

**Initial brief**: v1.0 → v1.1 gross jumped 12.6 %/yr → 23.0 %/yr (+10.4 pp), yet v1.1 was supposed to be a turnover-reduction patch.

**Apples-to-oranges identified**: 12.6 %/yr was `base.cagr` (net of all costs) of v1.0. 23.0 %/yr was `gross_price_pnl_ann` (price leg only) of v1.1. They are different metrics. The real gross_price_pnl_ann v1.0 was **19.5 %/yr** — not 12.6.

**Diagnostic trials** (`H-20261020-006..013`, ledger lessons logged for 006-009):

| trial | config | gross_price | cost_drag | CAGR | Sharpe | turnover |
|---|---|---|---|---|---|---|
| 010 V1d | v1.0 re-run (vol=60, no band, daily) | **19.5 %** | 4.74 % | 12.6 % | 0.702 | 31.6× |
| 011 V1a | band only (vol=60, daily) | **19.5 %** | 4.73 % | 12.6 % | 0.702 | 31.6× |
| 012 V1b | weekly only (vol=60, no band) | **25.0 %** | 1.52 % | 22.6 % | 1.062 | 10.1× |
| 013 V1c | vol lookback only (vol=180, no band, daily) | **18.5 %** | 4.21 % | 12.3 % | 0.710 | 28.1× |
| 004 v1.1 full | band+weekly+vol=180 | **23.0 %** | 1.35 % | 20.7 % | 1.046 | 9.0× |

**Decomposition** (gross_price_pnl_ann, the apples-to-apples metric):

| effect | gross_price_delta |
|---|---|
| weekly rebalance (V1b − V1d) | +5.5 pp |
| band (v1.1 − V1b) | −2.0 pp |
| vol_lookback (V1c − V1d) | −1.0 pp |
| **total gap (v1.1 − v1.0)** | **+3.5 pp** (matches 23.0 − 19.5) |

**Band alone (V1a) is a no-op without weekly** — daily-rebalanced weight changes are ≈0.01-0.05, below the 0.02 band threshold in the few cases the band would actually fire.

**Weekly rebalance alone (V1b) explains almost all the gross-price improvement AND drops turnover from 31.6× to 10.1×** (cost drag 4.74 → 1.52 %). Weekly batches the next signal into a Monday-only rebalance instead of churning every daily bar.

**Band + weekly together** (v1.1 full) reduces gross slightly (−2 pp) because the band now prevents some intra-week flips, but the net Sharpe is best (1.046 vs 1.062 for V1b) because the 17 bps extra cost savings compound.

**Vol lookback (180 vs 60)** is **cosmetic or mildly negative** on gross — it shrinks the vol target slightly, leaving more in cash. The main effect is on stability, not return.

**Bug `scaled.reindex(columns=perp_cols)` myth**: I initially attributed part of the jump to a "bug fix" in v1.1. After `git show 18cd2a2:src/aster/strategies/vol_target_trend_ensemble.py`, I confirmed v1.0 had no rebalance state machine and no such code path. The hypothesis is retracted. The 100 % of the gap is the param trio above, dominated by weekly.

**Conclusion V1**: weekly rebalance is the dominant driver of the Sharpe jump; the +10.4 pp question was based on a wrong baseline metric.

## V3 — Is it just beta? — DONE 2026-10-20

Net returns of F3 v1.1 (`backtests/H-20261020-004/.../returns.csv`) against two benchmarks over [2017-08-18, 2024-06-30]:

| metric | F3 v1.1 net | BTC b&h | EW5 b&h |
|---|---|---|---|
| Sharpe_ann | 1.046 | 0.901 | **1.175** |
| Vol_ann | 10.4 % | 37.9 % | 37.7 % |
| Mean daily | 0.057 % | 0.179 % | 0.232 % |
| beta vs F3 | 1.000 | **0.029** | 0.053 |
| corr | 1.000 | 0.107 | n/a |
| alpha vs F3 (per year) | – | +18.9 % | +16.3 % |
| alpha HAC t-stat | – | **+2.70** | **+2.36** |

**F3 is NOT just BTC or EW5 beta.** Beta(F3, BTC) = 0.029 (~3 %), correlation 0.107. The trend signal adds alpha that is HAC-significant at the 5 % level on both benchmarks.

**However**: EW5 buy-and-hold has a **higher** Sharpe (1.175 vs 1.046) on the same window. F3's edge is in (i) much lower vol (10.4 % vs 37.7 %), (ii) lower drawdown (-22.6 % vs -65 %+ on EW5 in 2022), (iii) the HAC-significant alpha. The strategy is not strictly dominant in Sharpe, but it dominates on risk-adjusted terms if you penalize vol/drawdown — which is the actual purpose of a vol-targeted book.

## V5 — Capacity that actually varies with size — DONE 2026-10-20

**Found a bug** in the pipeline's AUM sweep: it uses `CostModel(fee=10bps, slip=5bps)` (constant), NOT `GridCostModel(research/atlas/cost-grid.csv)` which has grid rows from (symbol, utc_hour, notional_bracket). The grid exists in the repo (`research/atlas/cost-grid.csv`) and the cost_model has the class (`GridCostModel`), but the pipeline doesn't load it by default.

**Evidence** (`tests/test_v5_capacity_grid.py::test_v5_grid_model_sharpe_decreases_with_aum`, 23s):

| AUM | ConstantCostModel | GridCostModel |
|---|---|---|
| 100k | +1.183 | **+0.946** |
| 1M | +1.183 | +0.765 |
| 10M | +1.183 | +0.198 |
| 50M | +1.183 | **-0.798** |

**At 50M USD, F3 v1.1 has NEGATIVE Sharpe with the realistic cost grid**, while the pipeline reports +1.183 because it uses a constant cost. The current AUM sweep on `H-20261020-004` is misleading.

**Capacity at net Sharpe ≥ 1.0** is roughly **1M USD per side** with the realistic cost grid. The pipeline default must be fixed to use the grid before any AUM-sweep number is taken seriously.

**Test added**: `tests/test_v5_capacity_grid.py` — asserts Sharpe at 50M < Sharpe at 100k with `GridCostModel`. **594 passed / 1 skipped** after the addition.

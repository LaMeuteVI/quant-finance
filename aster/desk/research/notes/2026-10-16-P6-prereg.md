## 1. Why P6 exists

`research/QUEUE.md:52` records the verdict of the F1 v1 dev backtest: all-zero
weights and `sharpe_ann / DSR / walk_forward / PBO = None`. The current
pipeline never passes the funding panel to the strategy, never materialises
the funding store into the standard `data/funding/binance/<SYM>/8h.parquet`
layout (`store.load_funding` looks for that path but the partitions live in
`data/r2/market/futures/um/funding_rate/...`), and the engine computes
`held * funding` only when both the funding panel and the perp leg are
present. The P1/P2 DoD was therefore not met for any perp-aware strategy
(F1, F2, F1v2, and any future basis / premium / OI strategy).

`research/QUEUE.md:52` is the QUEUE definition of P6. The prereg below
fixes the engineering contract.

## 2. Mechanism

A funding-carry strategy holds a delta-neutral book (long spot / short
perp, or the reverse). The perp leg pays or receives funding at the
00:00 / 08:00 / 16:00 UTC fixings. The funding **rate** is the per-8h
return paid by longs to shorts (positive ⇒ longs pay). The economic
realities the pipeline must respect:

- Funding is **charged on perp legs only**, never on spot legs
  (engine contract from P2, enforced by `_normalise_perp_legs`).
- Funding is credited at the **fixing bar** (the close of the 00/08/16
  UTC hour, 8h after the previous fixing). A bar between two fixings
  carries no funding by itself — `ffill` is causal because the fixing
  is the *announcement* event, not the per-bar accrual.
- The strategy's *net* return is the **spot close return** minus the
  **perp close return** minus the **funding charge** on the perp leg
  plus costs. The engine must therefore have a `perp_close` panel in
  addition to the spot `prices` panel so the perp leg earns the perp
  return; without it the perp leg earns zero (a free put option) and
  the carry signal is artificially huge.
- A strategy that returns all-zero weights is an **infrastructure
  failure**, never a rejection (DECISIONS.md:17). The pipeline must
  raise a `PipelineError` instead of producing a report with all-None
  statistics.

## 3. Scope (this item only)

What P6 delivers:

1. **`aster.data.funding_materialise.materialise_funding_panel(exchange, symbols, timeframe)`**:
   reads the R2 Hive-partitioned funding store, reindexes to the
   requested bar frequency with a **causal** `ffill` (no `bfill`, no
   leakage of the next fixing), and writes the standard
   `data/funding/binance/<SYM>/<timeframe>.parquet` artefacts with a
   manifest. The column convention stays spot-symbol (`BTCUSDT`) for
   compatibility with `load_funding`; the strategy reads it and tags
   each column with the `:USDT` perp suffix when building weights.
2. **`aster.backtest.engine.run_backtest(..., perp_close=...)`**: an
   optional `perp_close` panel. When provided, the perp leg's per-bar
   return is `perp_close.pct_change()`; when absent, the perp leg
   earns zero return (legacy behaviour, kept for tests that don't
   care). The funding sign convention is unchanged: positive rate
   means longs pay.
3. **`aster.backtest.pipeline.run(...)` integration**:
   * loads the funding panel via the new `materialise_funding_panel`
     when the prereg has `perp_legs` set (any non-None value);
   * loads the perp close panel from the standard
     `data/ohlcv/binance/<SYM>:USDT/<timeframe>.parquet` (will be
     materialised by Q3b; until then `perp_close=None` is fine and
     the engine still produces a correct *basis+funding* P&L for
     the spot leg and a zero return on the perp leg);
   * passes both into `evaluate(...) → run_backtest(...)`;
   * **raises** `PipelineEmptyWeightsError` if the strategy returns
     a `target_weights` frame whose non-NaN entries are all zero;
   * passes the funding panel into the strategy as
     `kwargs["funding"]` (existing contract of F1 v1) **or** via
     `MarketData.funding` (new contract for F1v2 / F2 — whichever
     the strategy prefers).
4. **Integration test `tests/test_p6_perp_funding.py`**:
   * **Test A (P6 DoD)**: synthetic constant **+1 bps per fixing**
     funding series on a single symbol, 30 days of 1h bars starting
     2023-01-01. Strategy: long spot / short perp, full notional,
     no signal, held throughout. Expected net funding per day before
     costs = +3 bps (3 fixings × +1 bps), within 1 bps of the exact
     theoretical value (the engine rounds the bar-aligned funding
     between fixings).
   * **Test B (P6 DoD)**: strategy that returns all-zero weights
     makes `pipeline.run` raise `PipelineEmptyWeightsError`, with a
     message naming the strategy and the trial. No JSON report is
     written.
   * **Test C (defence)**: a non-zero-weight strategy that calls
     `target_weights(MarketData)` with `MarketData.funding` set
     receives the funding panel. A strategy that uses the legacy
     `kwargs["funding"]` channel still receives it. Both code paths
     must produce the same backtest result.
5. **`research/atlas/p6_perp_funding.json`** artefact: protocol +
   per-test result. Status: `GREEN` when every test passes,
   `RED` otherwise.

What P6 does **not** deliver:

- No perp close price materialisation (Q3b).
- No new hypothesis registered. No `H-*` ledger entry. No backtest
  on real data (F1v2).
- No change to `risk/`, `execution/`, `policies/`,
  `config/risk_limits.yaml`, no live, no key, no order, no paper.
- No `holdout` sample reading. The integration test uses synthetic
  data built in-memory, not the sealed store.

### 3.3 Carry bar (the gates, not a bps/year threshold)

The carry bar comes from `config/desk.yaml:gates`, not from a
fixed bps-per-year number. F1v2 must satisfy **all** of:

- `min_obs: 500`
- `sharpe_ann_min: 0.8`
- `max_drawdown_floor: -0.35`
- `dsr_min: 0.95` (DSR computed with the family count including F1 v1)
- `stress_sharpe_ann_min: 0.3` (×2 costs on the grid)

For context (informative, not a bar): Q8 measured +1.234 bps mean
funding per 8 h fixing ≈ 3.7 bps/day ≈ **13 %/yr gross**. After
base costs (Binance spot taker 10 bps/side + USDⓈ-M taker 5 bps/side,
slippage 5 bps/side each side), a 28-day holding round-trip on a
delta-neutral book costs ~30 bps = ~0.12 %/month. The implied **net**
carry is ~13 %/yr minus ~14 %/yr cost-of-turnover, which is roughly
break-even on a single pair. The desk gates (Sharpe, DSR, drawdown,
stress) are the binding test, not the bps number.

## 4. Falsification

P6 is **falsified** (i.e. the engineering contract is not met) if any
of:

- The integration test in §3.4 does not pass on the first or second
  run on the same commit. Persistent failure after a second attempt
  ⇒ `P6 RED`, the pipeline fix is escalated to Samuel.
- `pipeline.run` still produces a JSON report with `sharpe_ann=None`
  on a non-zero-weight strategy that consumes `kwargs["funding"]` or
  `MarketData.funding`.
- The materialised funding panel has any row with `index >= 2024-07-01`
  (cutoff breach).

## 5. Numeric prediction (for the integration test)

- Funding = +1 bps/fixing, 3 fixings/day, 30 days ⇒ +90 bps gross over
  30 days on the perp leg of a delta-neutral book held flat.
- Per-bar (1h) funding mean = +90e-4 / 720 = +1.25e-4 (matches the
  +1 bp / 8h spread over 8 bars).
- Net funding minus zero costs (the synthetic strategy has no
  rebalance after entry) = +90 bps ± 0.5 bps (numerical noise).
- The P6 DoD's "+3 bps/day before costs" is the same number
  expressed per day.

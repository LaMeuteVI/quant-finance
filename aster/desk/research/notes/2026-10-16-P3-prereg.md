# P3 — True holdout in the pipeline (preregistration)

**Date**: 2026-10-16
**Item**: P3 (research/QUEUE.md, Block P, critical path).
**Skills**: `quant-backtest-hygiene`, `lopez-de-prado-afml` ch11.

## Motivation

Today the pipeline's "holdout" is the last 25% of the pre-cutoff window, set
by `holdout_frac: 0.25` in `config/desk.yaml`. That window is **inside** the
range the exploration phase has already read: the preregistration,
backtest and review have all touched the data the dev gate is supposed to
protect. The audit (aster/AUDIT.md) flagged this as the most important
reproducibility failure left: a strategy that has been hand-tuned to the
late-pre-cutoff period can pass the dev gate without being valid.

The Q1 item (sealed-holdout machinery: `r2_klines.SEALED_STORE`,
`sealed_holdout_consumptions`, `consume_sealed_holdout`) shipped the
sealing mechanism but the pipeline does not yet use it. P3 wires the
sealed store into `pipeline.run`.

## Statement (what the dev gate is, mechanically)

The dev sample is the intersection of the preregistered universe with the
strictly pre-2024-07-01 data the bar bridge produced; nothing past the
cutoff may enter the dev run. The holdout sample is the sealed store
the agent has not seen, read **once** per hypothesis through
`Ledger.consume_sealed_holdout(symbol)`; the second call raises.

The pipeline's `holdout_start` is the desk-wide exploration cutoff
(2024-07-01 UTC), not the legacy 25% quantile of the price index. The
preregistration may NOT tighten it: the contract is single-sample, no
fishing, the cutoff is the same for every hypothesis.

## Mechanism (why a dev run cannot read a sealed row)

The bar bridge materialises pre-cutoff bars only, with a manifest that
embeds the cutoff in the source string (`cutoff_exclusive=2024-07-01T...`)
and rejects any row at or after the cutoff (`bars_from_minutes` raises
"no complete pre-cutoff bars" on a frame that crosses the boundary). The
sealed store lives at a different root (`data/sealed/...`) the generic
`store.read` cannot address: `store.dataset_path` raises if the resolved
path is under `data/sealed/`. The only way to read a sealed row is
`consume_sealed_holdout` (with a per-hypothesis consumption row written
to `sealed_holdout_consumptions`), and that function is only callable
from the `sample="holdout"` branch of `pipeline.run`, which requires
`status="backtest_passed"`.

## Falsification (what would falsify the contract)

P3 is rejected if any of these holds after the implementation:

1. `pipeline.run(..., sample="dev")` returns a row whose `index` is at or
   after 2024-07-01 UTC.
2. `pipeline.run(..., sample="holdout")` is reachable for a hypothesis
   whose `status != "backtest_passed"`.
3. The sealed store is readable by a path that does not go through
   `consume_sealed_holdout`.
4. `consume_sealed_holdout` is callable twice for the same (hypothesis,
   symbol) pair.

## Prediction (numeric)

- 1 test "dev cannot load a single sealed row" (synthetic 1d post-cutoff
  sealed Parquet, dev run must raise or return an empty dev sample).
- 1 test "holdout is reachable only after backtest_passed" (status
  preregistered → raise; status backtest_passed → OK; second call → raise).
- 1 test "holdout_start is 2024-07-01 UTC" (no override possible).
- 1 test "store.dataset_path refuses paths under data/sealed/".
- Existing 407 tests stay green (no regression on Q1..P2).

Total: 407 + 4 = 411 pytest green.

## Implementation scope

GREEN level (this commit):
- `pipeline.run` replaces `holdout_frac` with `CUTOFF` (the sealed cutoff).
- A new `pipeline._build_holdout_prices(ledger, hyp, symbols, timeframe)`
  helper reads the sealed store via `consume_sealed_holdout` and assembles
  the post-cutoff close panel the engine needs.
- `store.dataset_path` already refuses paths under `data/sealed/`; the
  helper bypasses that barrier via a sealed-only reader.
- Tests: see Prediction.

OUT of scope (left for P4/P5 and the F1..F3 hypotheses that follow):
- Sealed store population (the agent does not import the post-cutoff
  data; a separate downloader is required when the first F1/F2 candidate
  wants to consume the holdout, and the consumption itself is the
  irreversible act).
- Multi-symbol holdout assembly (a delta-neutral book would consume
  both the spot and the perp leg in the same call; P3 keeps the single-
  symbol contract from Q1).
